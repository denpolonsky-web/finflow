# Деплой FinFlow: полный гайд

Единственный актуальный документ по развёртыванию. Проект разрабатывался на Windows — здесь учтено всё, что из-за этого ломается при переносе на macOS.

Обновляется по мере работы. Журнал изменений схемы — в разделе 9: **именно он решает, нужно ли перед деплоем трогать базу.**

---

## 1. Статус на сегодня

**Что готово:** приложение собирается, 292 автотеста зелёные, линт чистый. Синхронизация покрыта сквозными тестами против подставного сервера: офлайн→онлайн, обрыв связи, отказ сервера, tombstone, защита локальных правок.

**Что нужно сделать руками перед первым деплоем** — четыре пункта, все обязательные:

| Блокер | Где закрывается |
|---|---|
| `node_modules` собран под Windows | Шаг 3 |
| Нет `.env` | Шаг 5 |
| Схема Supabase устарела: нет `goals.start_amount` и таблицы `categories` | Шаг 4 |
| Нет git-репозитория, а Vercel разворачивает из него | Шаг 6 |

**Чего ещё нет, и это важно понимать:** приложение **ни разу не работало против живого Supabase**. Все проверки синхронизации — локальные, против подставного сервера. Первый прод будет первой настоящей проверкой, поэтому приёмка (шаг 8) не формальность.

**Про разграничение доступа.** Профили (админ/работник) делят **интерфейс, а не данные**: все сидят под одной учётной записью Supabase и одним `user_id`, RLS у них одинаковый. Это защита от случайного взгляда на общем устройстве, а не от целенаправленного. Если работник — посторонний человек, которому ваши финансы видеть нельзя, нужна отдельная работа (эпик E1 в `CLAUDE.md`).

## 2. Данные при деплое не теряются

- **Vercel выкладывает только фронтенд.** К базе он не прикасается в принципе.
- **`supabase_schema.sql` идемпотентен**: везде `create table if not exists`, `add column if not exists`, `create or replace function`. Команд, удаляющих данные, в нём нет.
- Единственные `drop table` (для старых `cards` и `deposits`) **закомментированы**. Не раскомментируйте их, пока не убедитесь, что данные оттуда перенесены.

Два правила:

1. **Сначала SQL, потом фронтенд.** Если выложить новый фронт раньше схемы, цели и категории начнут отвергаться сервером и осядут в dead-letter. В облаке ничего не пропадёт, но выглядеть будет как «не синхронизируется», и из очереди их легко выбросить руками — вот тут уже теряются локальные правки.
2. **Локальная база ≠ облако.** «Сбросить локальную базу» и выход из аккаунта чистят только устройство.

## 4. Supabase

### 4.1. Проект

Если проекта ещё нет: supabase.com → **New project**. Регион — ближе к пользователям. Пароль БД сохраните, он понадобится только для прямого доступа к Postgres.

### 4.2. Схема

Supabase → **SQL Editor** → **New query** → вставить **целиком** содержимое `supabase_schema.sql` → **Run**.

**Выполнять обязательно, даже если файл применялся раньше.** Повторный запуск безопасен и идемпотентен. Актуальная версия добавляет колонку `goals.start_amount` и таблицу `categories`.

Создаются **9 таблиц**: `accounts`, `profiles`, `transactions`, `postings`, `goals`, `categories`, `budgets`, `balance_snapshots`, `app_settings`.

Плюс: индексы по `(user_id, updated_at)`, триггер `set_updated_at` на каждой таблице, политики RLS и функция `purge_tombstones()`.

### 4.3. Проверка, что схема применилась

Выполните в SQL Editor:

```sql
-- 1. Новое из последних правок: обе строки должны дать ok = 1
select 'goals.start_amount' as item, count(*) as ok
  from information_schema.columns
 where table_name = 'goals' and column_name = 'start_amount'
union all
select 'table categories', count(*)
  from information_schema.tables
 where table_schema = 'public' and table_name = 'categories';
```

```sql
-- 2. RLS включена на всех таблицах: rowsecurity должно быть true везде
select tablename, rowsecurity
  from pg_tables
 where schemaname = 'public'
 order by tablename;
```

```sql
-- 3. У каждой таблицы ровно 4 политики (select/insert/update/delete)
select tablename, count(*) as policies
  from pg_policies
 where schemaname = 'public'
 group by tablename
 order by tablename;
```

Если где-то `ok = 0`, `rowsecurity = false` или политик меньше четырёх — **схема не применилась полностью, деплой откладывается.** Это не косметика: RLS — единственное, что закрывает ваши финансы от чужого anon-ключа.

### 4.4. Пользователи

Регистрации в приложении нет намеренно. Заводим руками:

**Authentication → Users → Add user → Create new user**
- email и пароль
- **обязательно** галочка **Auto Confirm User** — без неё вход упрётся в «Email не подтверждён»

Повторите для каждого, кто будет входить. Напоминание: сейчас админ и работник входят под **одной** учётной записью, роли разделяют только интерфейс.

### 4.5. Выключить регистрацию

**Authentication → Sign In / Providers** → выключить **Allow new users to sign up**.

Иначе любой, кто откроет сайт, заведёт себе аккаунт в вашем проекте.

### 4.6. Ключи

**Project Settings → API**:
- **Project URL** → это `VITE_SUPABASE_URL`, вида `https://<ref>.supabase.co`
- ключ **anon** (он же publishable) → это `VITE_SUPABASE_ANON_KEY`

### 4.7. Чего делать нельзя

- **Не используйте `service_role` в приложении.** Он обходит RLS целиком. Его место — серверные скрипты, и только.
- **Не добавляйте политики вида `using (true)`.** Anon-ключ лежит в бандле у каждого, кто открыл сайт; такая политика открывает все финансы всем. Именно этот баг был в прошлой версии проекта.
- **Не отключайте RLS**, чтобы «отладить» — проще посмотреть сообщение об ошибке в приложении.

### 4.8. Опционально: уборка удалённых записей

Удаления едут между устройствами как tombstone'ы (`deleted_at`), и копятся вечно: функция `purge_tombstones()` в схеме есть, но её никто не вызывает. Раз в неделю достаточно.

Либо вручную в SQL Editor:

```sql
select purge_tombstones();
```

Либо по расписанию, через pg_cron:

```sql
create extension if not exists pg_cron;
select cron.schedule('purge-tombstones', '0 3 * * 0', $$select purge_tombstones()$$);
```

Функция удаляет только строки, помеченные удалёнными **более 90 дней назад** — запас на редко включаемые устройства.

## 5. Подготовка проекта на macOS

```bash
cd путь/к/finance-app
```

Снести зависимости, собранные под Windows, и мусор:

```bash
rm -rf node_modules package-lock.json
find . -name '.DS_Store' -delete
rm -rf __MACOSX
```

> `package-lock.json` сносится вместе с ними намеренно: он помнит платформенные пакеты. `npm install` создаст новый, с бинарниками под macOS.

Проверить Node — нужен **20 LTS или новее** (разрабатывалось на 24):

```bash
node -v
```

Нет или старее — `brew install node`.

Поставить зависимости и убедиться, что всё в порядке **до** деплоя:

```bash
npm install
npm test        # должно быть ~292 проверки, все зелёные
npm run lint    # без ошибок
npm run build   # это ещё и проверка типов
```

Если хоть одна команда красная — деплой откладывается до выяснения.

Переменные окружения локально:

```bash
cp .env.example .env
```

Заполнить значениями из шага 4.6 и проверить связь:

```bash
npm run dev
```

Признаки, что облако подключено:
- в консоли браузера `[cloud] сервер: <ваш-проект>.supabase.co`, а **не** «облако выключено»;
- вход проходит заведённым пользователем;
- Настройки → Синхронизация → «Всё синхронизировано».

## 6. Git

Vercel разворачивает из репозитория.

Готовый скрипт сделает `git init`, первый коммит и, если установлен `gh`, создаст **приватный** репозиторий:

```bash
bash setup-github.sh
```

Вручную:

```bash
git init -b main
git add -A
git commit -m "FinFlow"
git remote add origin git@github.com:<ваш-логин>/finflow.git
git push -u origin main
```

Перед пушем убедитесь, что секреты не попали в индекс:

```bash
git status --short | grep -i env
```

Пусто или только `.env.example` — хорошо. Если видите `.env` — остановитесь и проверьте `.gitignore`.

> Репозиторий делайте **приватным**. Anon-ключ в бандле — это нормально, его прикрывает RLS, но лишней публичности финансовому приложению не нужно.

## 7. Vercel

1. vercel.com → **Add New → Project** → импортировать репозиторий.
2. Настройки сборки менять не нужно: Vercel возьмёт их из `vercel.json` (`framework: vite`, вывод в `dist`, SPA-rewrites с исключениями для `sw.js`, `registerSW.js`, `manifest.webmanifest`, заголовки кэширования).
3. **Settings → Environment Variables** — добавить в **Production, Preview и Development**:

   | Имя | Значение |
   |---|---|
   | `VITE_SUPABASE_URL` | `https://<ref>.supabase.co` |
   | `VITE_SUPABASE_ANON_KEY` | anon-ключ |

   > Переменные Vite подставляются **на сборке**, а не в рантайме. Добавили или изменили — нужен **Redeploy**, иначе в бандле останутся старые значения.

4. **Deploy**.

## 8. Приёмка после деплоя

Это не формальность: против живого Supabase приложение работает впервые.

1. **Вход.** Экран входа показывает адрес сервера внизу — убедитесь, что он ваш.
2. **Запись доезжает.** Завести операцию → Настройки → Синхронизация → «Всё синхронизировано» → проверить строку в Supabase → **Table Editor → transactions**.
3. **Офлайн.** Выключить сеть, завести операцию (появится «Офлайн — данные сохраняются локально»), включить сеть, дождаться синхронизации, убедиться в облаке. **Запись не должна потеряться.**
4. **Второе устройство.** Открыть под тем же логином — операция должна приехать. Завести там операцию — должна приехать обратно.
5. **Удаление.** Удалить операцию на одном устройстве — она должна исчезнуть на втором.
6. **Цели.** Создать цель и убедиться, что строка появилась в `goals` — это проверка колонки `start_amount`.
7. **Категории.** Переименовать любую категорию в Настройках и убедиться, что строка появилась в `categories` — проверка новой таблицы.
8. **Смена аккаунта.** Выйти и войти другим пользователем — локальные данные должны очиститься, чужие операции видны быть не должны.
9. **PWA.** Safari → «Поделиться» → «На экран Домой».

Если что-то не сходится, Настройки → Синхронизация покажет конкретную причину, а не общее «ошибка».

## 9. Журнал изменений схемы

**Перед каждым деплоем сверьтесь с этим разделом.** Если в нём появилась строка, которой вы ещё не применяли, — сначала выполните `supabase_schema.sql` заново.

| Что | Зачем | Статус |
|---|---|---|
| `goals.start_amount` (bigint) | база для расчёта темпа цели; без неё темп считался от полного баланса привязанного счёта и выдавал бессмыслицу | **не применено на проде** |
| таблица `categories` + индекс, триггер, RLS, уборка tombstone'ов | свои категории и переопределения встроенных | **не применено на проде** |

После первого успешного деплоя отметьте обе строки как применённые.

## 10. Если пошло не так

| Симптом | Причина | Решение |
|---|---|---|
| Сборка падает сразу на маке | `node_modules` с Windows | `rm -rf node_modules package-lock.json && npm install` |
| «Облако выключено» в консоли | переменные не заданы или собрано до их добавления | Проверить переменные в Vercel → **Redeploy** |
| «Сервер отклонил ключ» | не тот ключ | Нужен **anon**, не `service_role` |
| «Email не подтверждён» | забыта галочка Auto Confirm | Authentication → Users → подтвердить вручную |
| Цели или категории не синхронизируются, в настройках «застряло записей» | схема старая | Выполнить `supabase_schema.sql`, затем Настройки → «Отправить всё заново» |
| Видны чужие данные | политика `using (true)` или RLS выключена | Проверки из шага 4.3, затем выполнить схему заново |
| После обновления открывается старая версия | кэш сервис-воркера | Закрыть все вкладки приложения и открыть заново |
| Пустой экран | ошибка в рантайме | Приложение покажет экран «Что-то сломалось» с текстом ошибки; подробности — в консоли браузера |

**Откат фронтенда:** Vercel → **Deployments** → предыдущий успешный → **Promote to Production**. База при этом не затрагивается.

**Откат схемы:** не требуется. Все изменения аддитивные — новые колонки и таблицы не мешают старому фронтенду.
