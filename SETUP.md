# Развёртывание FinFlow

Порядок важен: сначала база, потом переменные окружения, потом деплой.

---

## 1. Supabase

### 1.1. Схема и политики доступа

Supabase → **SQL Editor** → вставьте целиком `supabase_schema.sql` → **Run**.

Скрипт идемпотентный, данные не удаляет. Что он делает:

- создаёт таблицы `accounts`, `transactions`, `postings`, `goals`, `budgets`, `balance_snapshots`, `app_settings`;
- вешает на каждую `user_id uuid default auth.uid()`;
- **сносит старую политику `"owner" ... using (true)`** и ставит четыре политики на каждую таблицу: читать, вставлять, менять и удалять можно только свои строки;
- добавляет триггер `set_updated_at` — он гарантирует монотонность `updated_at`, без этого инкрементальная синхронизация может пропускать записи при расхождении часов на устройствах.

Старые таблицы `cards` и `deposits` скрипт **не трогает**. Удалите их вручную (команды закомментированы в конце файла) только после того, как убедитесь, что данные перенеслись.

### 1.2. Авторизация

Supabase → **Authentication → Providers → Email**:

- `Enable Email provider` — включить;
- `Confirm email` — на ваше усмотрение. Включено — надёжнее, но при регистрации придётся подтвердить письмо, прежде чем войти. Приложение этот сценарий обрабатывает и покажет подсказку;
- **Authentication → Rate Limits** — оставьте ограничение на попытки входа включённым, это защита от перебора пароля.

Пароль задаётся при регистрации прямо в приложении. Минимум 10 символов, очевидные варианты отсекаются на клиенте, остальное проверяет Supabase. Хэш (bcrypt) живёт в служебной схеме `auth`, в ваши таблицы и в бандл он не попадает.

### 1.3. Ключи

Supabase → **Settings → API**: скопируйте `Project URL` и `anon public`.

Anon-ключ попадает в клиентский бандл — так и задумано. Безопасность обеспечивают RLS-политики из пункта 1.1, а не секретность ключа. `service_role` ключ в приложение **не кладите никогда**.

## 2. Переменные окружения

Vercel → проект → **Settings → Environment Variables**. Добавьте в **Production, Preview и Development**:

```
VITE_SUPABASE_URL=https://xxxxxxxx.supabase.co
VITE_SUPABASE_ANON_KEY=eyJhbGci...
```

Критичный момент: **Vite подставляет эти значения на этапе сборки**, а не в рантайме. Если добавить переменные после деплоя — нужно нажать **Redeploy**, иначе в собранном бандле останется «облако не настроено» и приложение будет работать локально. В предыдущей версии проекта это уже случалось: в собранном `dist` был зашит `hasSupabase: false`, и вся синхронизация была вырезана из бандла как мёртвый код.

Локально: `cp .env.example .env` и заполнить.

## 3. Деплой

```bash
npm install
npm test        # 34 проверки: бухгалтерия и миграция
npm run build
```

Vercel подхватит `vercel.json` сам: `framework: vite`, вывод в `dist`, SPA-rewrites с исключениями для `sw.js`, `registerSW.js`, `manifest.webmanifest` и статики.

## 4. Первый запуск и перенос данных

Старая база в браузере (`FinFlowDB` v2) мигрирует автоматически при первом открытии новой версии:

- карты и вклады → счета (`accounts`);
- суммы из рублей-float → копейки-integer;
- каждая операция → транзакция + проводки, перевод получает обе ноги;
- `openingBalance` считается как `старый_баланс − Σ проводок`, поэтому **видимые балансы не изменятся**;
- операции, ссылавшиеся на несуществующий счёт (например, зашитый `'vtb'`), не теряются — под них создаётся восстановленный счёт, который можно переименовать или слить вручную;
- булевы флаги → `0/1`, потому что IndexedDB не индексирует boolean.

После миграции и первого входа приложение само зальёт локальные данные в облако (однократно, помечается флагом `initialPushDone`). Повторить вручную можно в **Настройки → Синхронизация → Отправить всё заново**.

Перед обновлением имеет смысл зайти в старую версию и выгрузить данные, если такая возможность там была; в новой версии экспорт JSON/CSV есть в настройках.

## 5. Проверка, что всё взлетело

1. Открыть приложение → экран входа → зарегистрироваться.
2. Создать счёт с остатком, добавить расход — баланс уменьшился.
3. Создать второй счёт, сделать перевод — **общий баланс не изменился**.
4. Открыть ту же учётку на другом устройстве → данные приехали.
5. Supabase → Table Editor → `postings`: строки есть, у всех заполнен `user_id`.
6. Выключить сеть, добавить операцию → баннер «Ожидает отправки», включить сеть → счётчик обнулился.

Если на шаге 4 данные не приехали: **Настройки → Синхронизация** показывает статус, количество локальных записей и текст последней ошибки — этого достаточно, чтобы понять, упёрлось оно в RLS, в отсутствующую таблицу или в сеть.
